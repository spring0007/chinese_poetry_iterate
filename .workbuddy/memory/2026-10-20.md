### 评估：authors 按 dynasty 筛是否该改 id 区间（09:55，结论：不改）
- **不可行**：`authors.id` 是 `enumerate(authors)` 的导入顺序序号（build.py:574），与朝代**无任何编码关系**；实测前 15 行 id=1..15 全是 tang（因为作者源文件先唐后宋），但 id 段与朝代不对应。要 id 区间就得重排 id。
- **重排代价**：① `store.py:350/529` 按 authors.id 回跳改 n_poems；② `build.py:760` snapshot 恢复按 `ORDER BY id` 决定同名跨朝代的"后者覆盖"语义；③ `query.py:_author_of` 把 author_id 返给 UI 当编辑键；④ 外部按 author_id 存的引用全错位（正是 v3.4 引入 author_uid 要解决的位移问题）。而且同朝代内每次增删仍位移，只买到"朝代内稳定"。
- **收益实测**（14,373 行内存副本，500 次均值）：全表扫 tang 3.49ms / song(69%) 7.73ms / count 0.90ms；单列 `dynasty` 索引 SEARCH 2.70ms（song 7.95ms，无改善）；`(dynasty,name)` 覆盖索引 + order by name 2.44ms；**模拟 id 区间（dyn<<20|seq）2.37ms、count 0.09ms**。→ 瓶颈是结果集构造（3,712 行），不是 B-tree 下行，id 区间最多省 1.1ms。
- **结论**：authors 不做 id 区间。真要做"按朝代列作者"，用分页 LIMIT + 可选 `(dynasty,name)` 或 `(dynasty,score DESC)` 索引即可（14K 行建索引 <10ms）。poems 用 id 区间是因为 3.7 已删 dynasty_id 列、id 天然编码朝代，是零成本副产品；authors 有 dynasty TEXT 列在手且基数仅 16，处境不同，不构成"该统一"的理由。
- 未改任何代码/DB（纯评估）。

### 修 authors.dynasty 的 15 个非法值（10:10–10:20）
- **决策**：用户否决"新建 dynasty 表"，只修脏数据——即把 `chuci/nalan/mengxue` 三个非朝代值归位。
- **根因**：`sources.py` 的 `AuthorSource(name, dynasty, pattern)` 第二参数是 dynasty，但 `chuci.authors/nalan.authors/mengxue.authors` 三个源填成了来源名。15 位作者（楚辞 9 / 蒙学 5 / 纳兰 1）的 `authors.dynasty` 因此落在 `schema.DYNASTY` 之外，`make_author_uid` 的派生键也带上垃圾串。3.5→3.7 三次重建全 PASS，因为 verify_db 当时**没有** authors.dynasty 的断言。
- **修法**：三个值对齐所属 Collection——`chuci→preqin`、`nalan→qing`、`mengxue→unknown`（蒙学集合本身即 unknown，作者跨南朝梁/明/清三代，不臆断）。
- **代码改动**：`sources.py` 三行 + 注释（写明第二参数语义与后果）；`verify_db.py` 新增「authors.dynasty 全部落在 schema.DYNASTY 内」断言 + 按朝代分布打印；`schema.py` 朝代表注释补例外说明；新建 `test_sources.py`（11 例：Collection/AuthorSource 的 dynasty/kind/genre 合法性、作者源与同名集合 dynasty 一致、三处历史错值钉死、DYN_BITS 不溢出）；`poet_tiers.py` 与 `author_heat.py` 新增 `--db` 参数。
